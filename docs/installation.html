Installation

Build Toolchain

The project uses the .NET 10 SDK with the Microsoft.NET.Sdk.Worker project type. Deterministic builds with locked NuGet restore (packages.lock.json).

Central Package Management (CPM) is enabled via Directory.Packages.props at the repo root. All NuGet version numbers are declared there — individual .csproj files reference packages without version attributes. Dependabot targets the CPM file directly, producing grouped PRs per package family.

Build & Publish

# Restore (locked mode — requires packages.lock.json)
dotnet restore -p:RestoreLockedMode=true

# Run tests
dotnet test -c Release

# Publish optimized self-contained single-file executable
dotnet publish src/JenkinsAsService `
    --nologo --configuration Release `
    -p:RestoreLockedMode=true `
    --runtime win-x64 --self-contained true `
    --output publish/x64/ `
    -p:PublishSingleFile=true `
    -p:EnableCompressionInSingleFile=true `
    -p:PublishReadyToRun=true `
    -p:OptimizationPreference=Speed `
    -p:UseSharedCompilation=true `
    -p:DebuggerSupport=false `
    -p:MetadataUpdaterSupport=false `
    -p:Deterministic=true `
    -p:DebugType=Embedded `
    -p:DebugSymbols=true `
    -p:InformationalVersion="1.0.0" `
    /v:q /clp:ErrorsOnly

# Build MSI installer (requires WiX v5 SDK — auto-restored via NuGet)
dotnet build src/JenkinsAsService.Installer -c Release -p:PublishDir=../../publish/x64/ -p:Version=1.0.0

These are the exact flags CI uses: both workflows call the local composite action .github/actions/publish, so the binary validated on a PR is built identically to the one attached to a release. build.yml exists to mirror the release steps, and a flag drifting between the two would defeat that.

Publish Flags

Flag Purpose

EnableCompressionInSingleFile Compresses the bundle
PublishReadyToRun AOT pre-compilation (R2R) for faster startup

  • JenkinsAsService.exe — Self-contained executable (~42MB, no .NET runtime needed)
  • appsettings.json — Configuration template

Central Package Management + locked restore

Versions are pinned (no floating ranges) and declared centrally, so .csproj files reference packages without a Version attribute — adding one is an error. The app, test and installer projects each carry a packages.lock.json for deterministic, hash-verified restores under RestoreLockedMode=true; adding or bumping a package means regenerating the lock files (dotnet restore --force-evaluate).

MSI Installer

The project includes a WiX v5 MSI installer (src/JenkinsAsService.Installer/) that:

  • Installs to C:\Program Files\Jenkins (customizable via install directory dialog or INSTALLFOLDER property)
  • Registers the Jenkins Windows Service under a least-privilege virtual service account (NT SERVICE\Jenkins, Automatic start) instead of LocalSystem
  • Splits binaries from runtime data: binaries stay read-only in C:\Program Files\Jenkins (the agent account cannot overwrite the .exe), while runtime artifacts live in a separate writable data folder C:\ProgramData\JenkinsAsService (overridable via DATAFOLDER) where the service account is granted write — logs and the secret file at the root, the cached agent.jar (+ SHA-256) under agent\, and the agent -workDir under work\
  • Locks down appsettings.json so only SYSTEM, Administrators and the service account can read it (the secret-bearing file is removed from Users)
  • Pre-creates the Windows Event Log source (the low-privilege account cannot create it at runtime)
  • Configures Windows-level service recovery automatically (util:ServiceConfig — restart on all 3 failures after 10s, reset daily)
  • Starts the service after install
  • Stops and removes the service on uninstall — see What uninstall removes
  • Supports in-place upgrades (same UpgradeCode across versions), reconciling appsettings.json to the new schema without disturbing your settings or secret
  • Default secret protection mode: Dpapi (machine-scoped encryption at rest)
Configuration on upgrade

An in-place upgrade reconciles the existing appsettings.json to the new version's schema: settings introduced in the release appear at their defaults, settings the schema no longer defines are removed, and your existing values — including the secret — are preserved. The secret is detected by a decryption-free presence check, so a secret bound to the service account (User-scope DPAPI, TPM, or Credential Manager) survives the upgrade untouched; if no secret is present, the upgrade writes a fresh configuration from the supplied properties. Because unknown keys are pruned, configure only documented settings. See Configuration → Config migration on MSI upgrade.

Service account

The default NT SERVICE\Jenkins virtual account needs no password and no Active Directory. For a domain gMSA or a dedicated password-based account, override SERVICE_ACCOUNT (plus SERVICE_ACCOUNT_DOMAIN / SERVICE_ACCOUNT_NAME for the folder ACL, and SERVICE_PASSWORD — leave empty for gMSA).

MSI Dialog Flow

LicenseAgreementDlg → InstallDirDlg → JenkinsConfigDlg → SecurityOptionsDlg → AdvancedOptionsDlg → VerifyReadyDlg

RequiredFieldDlg interrupts the flow when a mandatory field (URL, secret) is left empty. The Advanced Options page covers transport, certificate pin, Secret:ViaFile, environment sanitization, logging and recovery — applied after the main config write by three deferred update-secret --merge custom actions (split only to stay under the MSI 255-character command-line limit), which run before the service starts.

Installation

MSI (Recommended)

  1. Download the .msi for your architecture from Releases
  2. Run the installer — it walks through install path, Jenkins URL, agent secret, and secret protection mode
  3. Done — the service registers and starts automatically

Silent Install

For automated deployments, use msiexec with public properties:

msiexec /i JenkinsAsService_1.0.4_x64.msi /qn `
    INSTALLFOLDER="D:\Jenkins" `
    DATAFOLDER="D:\JenkinsData" `
    JENKINS_URL="https://jenkins.example.com:8443" `
    JENKINS_SECRET="your-secret" `
    JENKINS_SECRET_MODE="Dpapi" `
    JENKINS_THUMBPRINT="" `
    JENKINS_AGENT_NAME="" `
    JENKINS_JAVA_PATH=""

For a domain gMSA, add the identity properties (note the trailing $ and empty password):

msiexec /i JenkinsAsService_1.0.4_x64.msi /qn `
    JENKINS_URL="https://jenkins.example.com:8443" `
    JENKINS_SECRET="your-secret" `
    SERVICE_ACCOUNT="CONTOSO\svc-jenkins$" `
    SERVICE_ACCOUNT_DOMAIN="CONTOSO" `
    SERVICE_ACCOUNT_NAME="svc-jenkins$" `
    SERVICE_PASSWORD=""
Property Required Default Description
INSTALLFOLDER No C:\Program Files\Jenkins Installation directory for the (read-only) binaries
DATAFOLDER No C:\ProgramData\JenkinsAsService Writable data directory root (logs + secret file at the root, cached agent.jar under agent\, agent -workDir under work\). The service account is granted write here; persisted to Agent:DataDirectory in appsettings.json
JENKINS_URL Yes — Jenkins controller URL with explicit port
JENKINS_SECRET Yes — JNLP agent secret
JENKINS_SECRET_MODE No Dpapi Dpapi (default), Tpm (hardware-backed), CredentialManager, EnvironmentVariable, or Unprotected
JENKINS_THUMBPRINT No — SHA-256 thumbprint of the controller TLS certificate to pin the agent.jar download (empty = standard chain validation)

Keeping the secret out of the MSI log

The install-time secret travels on a deferred custom-action command line — an accepted MSI trade-off, mitigated by Hidden="yes" and running as SYSTEM without impersonation. A scripted install that must avoid even a verbose MSI log should install without JENKINS_SECRET and then call update-secret --secret-file or --secret-env directly.

Portable (Archive)

For environments where MSI installation isn't possible, download the .7z or .rar archive from Releases:

  1. Extract to a folder of your choice (e.g. D:\Jenkins)
  2. Edit appsettings.json — fill in Connection:Url, Secret:Value, and any other settings
  3. Register and start the service:
# Least-privilege virtual service account (matches the MSI default). Use obj= LocalSystem only if required.
sc.exe create Jenkins binPath= "D:\Jenkins\JenkinsAsService.exe" start= auto obj= "NT SERVICE\Jenkins"
sc.exe failure Jenkins reset= 86400 actions= restart/10000/restart/10000/restart/10000
sc.exe start Jenkins
Low-privilege account prerequisites

A virtual / low-privilege account cannot create the Event Log source. When not using the MSI, run update-secret --silent from an elevated prompt once (it pre-creates the Event Log source and writes appsettings.json). Runtime artifacts (logs, agent.jar, work dir) go to the separate writable data folder %ProgramData%\JenkinsAsService, which the service creates itself — no write access to Program Files is required at runtime. The service falls back to file-only logging if the Event Log source is unavailable.

To configure secret protection and harden the config ACL, run the CLI (elevated) before starting:

.\JenkinsAsService.exe update-secret --secret "your-secret" --url "https://jenkins:8443" --mode Dpapi --service-account "NT SERVICE\Jenkins" --silent

To uninstall:

sc.exe stop Jenkins
sc.exe delete Jenkins

What uninstall removes

Uninstalling (Add/Remove Programs, or msiexec /x) stops and deregisters the service and removes everything — the install folder and the runtime data folder both. Nothing is left behind to clean up by hand:

LocationOn uninstallWhy
C:\Program Files\Jenkins (install folder) Removed, including appsettings.json The config may hold an encrypted secret, so it goes with the product
The Jenkins service Removed (stopped first) Standard ServiceControl behaviour
The secret, in whichever store Secret:Mode used Removed — TPM key, Credential Manager entry, or machine environment variable Unprotected and Dpapi keep the material in the config, which goes with the install folder. The other modes store only a pointer there, so deleting the file alone would leave a working agent credential on the machine
C:\ProgramData\JenkinsAsService (data folder) Removed — logs, cached agent.jar, the work\ directory and the runtime secret file Uninstalling means removing the product, not leaving a build workspace and a secret-bearing folder orphaned on disk
Save your logs and workspace first

Uninstall is destructive: the work\ directory (build workspaces, remoting/ state) and every rolled log file go with it. Copy anything you need out of %ProgramData%\JenkinsAsService before uninstalling — the MSI does not prompt.

How this works, and why an upgrade is safe

Neither the config nor the data folder is a tracked MSI file — appsettings.json is written by a custom action and the data tree is created at runtime — so Windows Installer alone removes neither. A deferred custom action sequenced just before RemoveFiles runs the purge command to delete both.

It is conditioned on REMOVE="ALL" AND NOT UPGRADINGPRODUCTCODE. That second clause is what keeps an upgrade safe: a major upgrade removes the old product first, and without the gate that removal would delete the config the upgrade is meant to reconcile, along with your logs and cached agent.jar. An in-place upgrade therefore preserves the data folder in full; only a genuine uninstall clears it. Both behaviours are asserted on every CI run — see CI/CD → MSI install / upgrade / uninstall.

A relocated Agent:DataDirectory is honoured: the purge reads the configured path and removes that tree. It refuses to delete a drive root or a well-known system directory, so a mistyped path leaves data behind rather than taking the machine with it.

The same read happens for the secret: Secret:Mode and Secret:Value are read before the config is deleted, because for the pointer modes that value names the environment variable or credential target to remove.

One case the uninstall cannot finish for you

Credential Manager entries are per-user, and the uninstall runs as SYSTEM. A credential written under another account (update-secret --impersonate) is not in SYSTEM's vault and cannot be removed from there. The purge reports this rather than passing silently, and prints the command to run while logged on as that account:

cmdkey /delete:JenkinsAsService/AgentSecret

Automated Release

The GitHub Actions release workflow (.github/workflows/release.yml):

  1. Push a tag matching v* (e.g., v1.0.4)
  2. Runs tests, publishes optimized self-contained executables for x64 and x86
  3. Builds MSI installers for both architectures via WiX v5
  4. Creates .7z (LZMA2, max compression) and .rar (RAR5 with 5% recovery record) archives
  5. Generates a CycloneDX SBOM for the service project
  6. Generates checksums.json with SHA256 hashes for all artifacts (SBOM included)
  7. Creates GitHub Release with auto-generated release notes

Service Recovery (Windows-Level)

The MSI installer configures Windows service recovery automatically via util:ServiceConfig:

  • First / Second / Third failure: Restart the Service (after 10 seconds)
  • Reset fail count after: 1 day
Note

The built-in watchdog handles Java process crashes. Windows-level recovery covers full service host crashes (the .NET process itself dying) — rare but covered automatically.
