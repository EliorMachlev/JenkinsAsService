CI/CD and Security Scanning

GitHub Actions Workflows

The repository has ten workflows covering build, test, docs quality, security scanning, and release automation.

.NET Build (.github/workflows/build.yml)

  • Purpose: Full end-to-end build validation on every push/PR to main
  • Runner: windows-latest
  • Steps: Setup .NET 10 → dotnet restore -p:RestoreLockedMode=true → dotnet test → CycloneDX SBOM (uploaded as artifact) → optimized publish (win-x64 + win-x86) → WiX v5 MSI build (both architectures, Version=0.0.0)
  • Tests: the full xUnit suite (xUnit + NSubstitute + FluentAssertions) — a failure blocks the publish and MSI steps
  • Note: Mirrors every compile and package step in the release workflow so failures surface on PRs, not at release time — see the shared publish action for how that mirroring is enforced rather than merely intended.

Shared publish action (.github/actions/publish)

Both workflows publish the executable through one local composite action rather than repeating the flag list. The set previously lived in five near-identical copies across build.yml and release.yml; since build.yml exists precisely to mirror the release compile and package steps, a flag drifting between the two would have defeated the point of having it. One definition means the binary validated on a PR is built exactly like the one attached to a release.

  • Inputs: runtime (win-x64 / win-x86), output, and an optional version stamped as InformationalVersion — omitted, the project value applies.
  • Fixed flags: self-contained single-file, ReadyToRun, compression, speed-optimized, deterministic, embedded PDB, and locked restore. The exact list is in Installation → Build & publish.
  • The msi-lifecycle job uses the same action, so the MSI it installs contains the shipped binary rather than a cheaper approximation of it.

Shared MSI action (.github/actions/build-msi)

The installer build was repeated six times across the two workflows, and every copy had to remember one non-obvious rule: the intermediate directory must be unique per package. PublishDir, InstallerPlatform and Version reach the build as MSBuild properties, which the up-to-date check does not track — so a shared obj/ turns the second build into a sub-second no-op that copies the first package to the new output directory. The action derives the intermediate path from its own inputs, so the rule cannot be forgotten by the next person to add a build step.

  • Inputs: publish-dir, platform (x64/x86), version, output.
  • Why it matters: that defect shipped. Every release published an x86 installer that was a byte-identical copy of the x64 package, and the msi-lifecycle job's first run performed a maintenance-mode reconfigure instead of an upgrade — while reporting its assertions as passed.
  • MSI identity is read through one module, .github/scripts/MsiQuery.psm1 (Get-MsiProperty, Get-MsiPlatform), used by both the platform check and the lifecycle test. The same COM interop previously existed in three places, which is how two copies came to ask slightly different questions about the same packages.

MSI Install / Upgrade / Uninstall (build.yml, second job)

  • Purpose: Actually install the MSI. ServiceSettingsNormalizer is unit-tested, but custom-action sequencing during a real in-place upgrade (WIX_UPGRADE_DETECTED gating, UpgradeConfig before StartServices, the config surviving RemoveExistingProducts) is only reachable by installing — which is why the upgrade path stayed on the “not verified” list for so long.
  • Flow: publish x64 → build the MSI at 1.0.0 and 1.0.1 → install 1.0.0 → edit the config as an operator would → upgrade in place → uninstall.
  • The upgrade is run with no properties at all — no URL, no data folder, and above all no JENKINS_SECRET. That matches the wizard, which shows no configuration pages on an upgrade, and it is the stronger assertion: supplying the same values twice made a preserved value indistinguishable from a re-written one. The wizard itself is never displayed by a /quiet job, so its upgrade gating is checked separately by reading the package's ControlEvent table and asserting that every route into the configuration pages carries NOT WIX_UPGRADE_DETECTED — which also catches the custom pages being dropped from the package altogether.
  • Asserted: the two packages really differ in ProductVersion (checked before anything is installed — identical versions would make the upgrade a no-op reconfigure whose assertions all still pass); the service registers and is Running (a stopped service means startup itself broke); edited values, the secret and the data folder survive the upgrade; a schema key missing from the old config is re-added at its default; an unknown key is pruned; the installed ProductVersion really advanced; and uninstall removes the service, the install folder and the data folder.
  • Cross-architecture migration policy — both halves of the asymmetric gate. First it installs x64 and points the x86 package at it, asserting the install is refused both without and with FORCE_UPGRADE=1 (that direction cannot recover the install folder, so the flag must not be a way through) and that each refusal is inert — product still x64, service still running, config untouched. Then it installs x86 and migrates to a higher x64 package: refused without the flag, and with it succeeding onto the original install and data folders with the config, operator edits and secret intact, the architecture confirmed from the binary’s PE header. A gate that never blocks and a gate that blocks everything would each pass on half the suite.
  • The upgrade/uninstall pair is the point. The purge custom action must fire on a real uninstall and never during an upgrade's removal of the old product; asserting only one of the two would let the opposite defect through unnoticed.
  • No controller needed: the URL points at a closed port, so the agent never connects — every assertion is about files, the registry and SCM. Verbose msiexec logs are uploaded as an artifact when the job fails.

Release (.github/workflows/release.yml)

  • Purpose: Automated dual-architecture release
  • Triggers:
    • Tag push — any tag matching v* (e.g. v1.0.5). Version is taken verbatim from the tag name.
    • Manual (workflow_dispatch) — optional version input:
      • If provided (e.g. 1.05): used verbatim as the release version.
      • If omitted: auto-bumps the latest published non-prerelease release by +1 on the final segment, preserving zero-padding (e.g. 1.03 → 1.04).
  • Runner: windows-latest
  • Steps:
    1. Setup .NET 10 → dotnet test
    2. Resolve version (from tag, explicit input, or auto-bump via gh api)
    3. Optimized publish for win-x64 and win-x86 via the shared publish action (R2R, compression, embedded PDB, deterministic, speed-optimized, locked restore)
    4. Build MSI installers for both architectures via WiX v5
    5. Create .7z archives (LZMA2, max compression) via 7-Zip
    6. Generate a CycloneDX SBOM (JenkinsAsService_<version>_sbom.json) and attach it to the release
    7. Generate checksums.json with SHA256 hashes for all artifacts (SBOM included)
    8. Create GitHub Release with all artifacts and auto-generated release notes
  • Tool: softprops/action-gh-release
  • Naming: JenkinsAsService_<version>_<arch>.<ext>

CodeQL Advanced (.github/workflows/codeql.yml)

  • Purpose: Vulnerability analysis across two language targets in a matrix:
    • language: actions (build-mode: none) — GitHub Actions workflow YAML files
    • language: csharp (build-mode: autobuild) — C# source code
  • Tool: github/codeql-action
  • Trigger: Push/PR to main, weekly schedule (Tuesdays 16:35 UTC)
  • Output: SARIF uploaded to GitHub Security → Code scanning results (one entry per language)

PSScriptAnalyzer (.github/workflows/powershell.yml)

  • Purpose: Static analysis of PowerShell code (full ruleset)
  • Implementation: Direct pwsh run: step — no action wrapper, no external modules. PSScriptAnalyzer is pre-installed on ubuntu-latest runners; SARIF 2.1.0 output is serialised inline in PowerShell using ConvertTo-Json and written to results.sarif, then uploaded via github/codeql-action/upload-sarif.
  • Trigger: Push/PR to main, Sundays at 23:23 UTC, workflow_dispatch (manual)
  • Output: SARIF uploaded to GitHub Security → Code scanning results (category: psscriptanalyzer)
  • Note: Replaces the unmaintained microsoft/action-psscriptanalyzer (last updated 2023; Microsoft’s ConvertToSARIF repo archived June 2026). No PSGallery dependency required.

Semgrep (.github/workflows/semgrep.yml)

  • Purpose: Pattern-based SAST — vulnerable code patterns, deprecated APIs, common weaknesses
  • Tool: semgrep/semgrep-action@v1
  • Trigger: Push/PR to main, Sundays at 04:38 UTC
  • Rules: p/default + p/csharp + p/secrets (community rulesets, no token required)
  • Output: SARIF uploaded to GitHub Security tab

Gitleaks (.github/workflows/gitleaks.yml)

  • Purpose: Secret and credential scanning across full git history
  • Tool: gitleaks/gitleaks-action@v3.0.0
  • Trigger: Push/PR to main, Sundays at 05:00 UTC
  • Coverage: fetch-depth: 0 — scans all commits

Dependency Review (.github/workflows/dependency-review.yml)

  • Purpose: Block PRs that introduce NuGet packages with known CVEs
  • Trigger: PRs to main
  • Tool: actions/dependency-review-action@v5
  • Database: GitHub Advisory Database (GHSA)

Trivy — SCA Full Scan (.github/workflows/osv-scanner.yml)

  • Purpose: Full-repo dependency vulnerability scan (on every PR/push + weekly)
  • Trigger: Push/PR to main, weekly schedule (Saturdays 23:28 UTC)
  • Tool: aquasecurity/trivy-action
  • Databases: NVD + GitHub Advisory + OSV
  • Output: SARIF uploaded to GitHub Security tab
  • Pattern: Calls trivy-reusable.yml via uses: ./.github/workflows/trivy-reusable.yml
  • Filename: the workflow is still called osv-scanner.yml for history — it declares name: Trivy and runs Trivy, which covers the OSV database among others. Nothing invokes the standalone OSV-Scanner.

Trivy — Reusable Workflow (.github/workflows/trivy-reusable.yml)

  • Trigger: workflow_call with inputs scan-type (default: fs) and scan-ref (default: .)
  • Steps: checkout → trivy → upload-sarif (if: always())
  • Versioning: all actions SHA-pinned (see Action Versioning Policy below)

HTML & CSS Lint (.github/workflows/html-lint.yml)

  • Purpose: Validate documentation HTML and CSS quality on every docs change
  • Trigger: Push/PR to main when any file under docs/ changes (path filter)
  • Runner: ubuntu-latest
  • Steps:
    1. W3C Nu HTML Checker — pip install html5validator, then html5validator --root docs/ --match "*.html". Wraps the official vnu.jar validator; catches malformed markup, invalid nesting, and missing attributes.
    2. Stylelint — npm install stylelint stylelint-config-standard, then npx stylelint "docs/*.css". Enforces modern CSS standards: no vendor-prefix shortcuts, modern rgb()/hsl() notation, range media queries (width <= N), no deprecated page-break-*, consistent selector specificity ordering, and kebab-case class naming.
    3. Internal link check — .github/scripts/check_doc_links.py (standard library only, no install, no new action pin). Nu validates markup and Stylelint validates CSS; neither notices an href pointing at a section that no longer exists. Verifies every internal link and every search-index.json URL resolves to a real page and a real id, and that no page defines the same id twice.
  • Config: .stylelintrc.json at repo root extends stylelint-config-standard with alpha-value-notation: number (keep .4 instead of 40%)
  • No new actions — uses only actions/checkout (already SHA-pinned); HTML and CSS tooling run via pip and npm directly, so no allowlist changes required

Software Bill of Materials (SBOM)

Both the build and release workflows generate a CycloneDX SBOM (spec 1.7, JSON) from the service project via the CycloneDX .NET global tool (version-pinned). The build workflow uploads it as a CI artifact (sbom-cyclonedx) on every push/PR; the release workflow attaches a versioned JenkinsAsService_<version>_sbom.json to the GitHub Release and includes its SHA-256 in checksums.json. This lets enterprise consumers enumerate every direct and transitive NuGet dependency and verify the artifact has not been tampered with in transit.

Code signing (planned)

Authenticode signing of the published .exe and MSI is on the roadmap. Since June 2023, code-signing keys must reside on FIPS-certified hardware (HSM/token), so signing runs through a cloud signing service (e.g. SignPath Foundation for OSS, or Azure Trusted Signing) wired into the release workflow and gated on a repository secret — the step stays inert until a certificate is provisioned. When wired, prefer a post-quantum-capable signing path (ML-DSA / CNSA 2.0) once the Authenticode and CA ecosystem supports it — as of 2026 it does not, so standard Authenticode applies. See Post-quantum cryptography for why in-process PQC was deferred.

NuGet Dependency Submission

GitHub automatically runs a platform-managed submit-nuget workflow (listed as dynamic in the Actions tab) that submits the resolved NuGet dependency graph to GitHub’s dependency graph API. This is not a workflow file in the repository — GitHub triggers it when a .csproj or packages.lock.json is present. It powers Dependabot alerts and the dependency graph view for this repo.

Action Versioning Policy

All actions are pinned to full commit SHAs to prevent supply-chain attacks via tag mutation (a tag like @v7 is mutable and can be silently redirected to malicious code; a SHA is immutable). The human-readable version tag is preserved as an inline trailing comment. Dependabot keeps the pins current via automated PRs — so the pins move every few weeks and are not reproduced here; read them from the workflow files, which are the only accurate source:

Select-String -Path .github/workflows/*.yml -Pattern 'uses:' | ForEach-Object { $_.Line.Trim() } | Sort-Object -Unique

The action set is small and deliberately so: actions/checkout, actions/setup-dotnet, actions/upload-artifact, actions/dependency-review-action, github/codeql-action/* (init / analyze / upload-sarif, always pinned to one consistent SHA), semgrep/semgrep-action, gitleaks/gitleaks-action, aquasecurity/trivy-action and softprops/action-gh-release. The rules for changing it:

  • Never replace a SHA pin with a floating tag, even temporarily.
  • New tooling should run through pip/npm/pwsh in a run: step rather than adding an action, when that is practical — this is why HTML/CSS linting and PSScriptAnalyzer need no new pins.
  • microsoft/psscriptanalyzer-action was removed entirely in favour of a direct pwsh step (see PSScriptAnalyzer above).
Note: Removed scanners
  • Codacy (codacy.yml) — removed. The native Codacy GitHub App ("SonarSharp reported by Codacy") is separate.
  • DevSkim — removed. Docker/MCR rate-limit issues; unmaintained. Replaced by Semgrep + Gitleaks.

Security Policy (Security.md)

  • Scope: JenkinsAsService executable, MSI installer, CI workflows. Jenkins/JDK/OS/third-party packages are out of scope.
  • Supported versions: Latest release only. Older versions are not patched.
  • Reporting: GitHub Private Vulnerability Reporting (preferred). No public issues for security bugs.
  • Response timeline: Acknowledge in 3 business days, assess in 7, patch within 30 days (critical/high) or 90 days (medium/low).
  • Coordinated disclosure: 90-day window, reporter can self-disclose after. Credit offered if desired.
  • Bounties: None (volunteer project).
