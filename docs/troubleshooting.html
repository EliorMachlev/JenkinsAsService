Troubleshooting

Log Files

The primary diagnostic tool is agent.log, written to the data directory — %ProgramData%\JenkinsAsService by default, or wherever Agent:DataDirectory points. It is not next to the executable: the install folder is deliberately read-only to the service account. Log format:

<PID> | <datetime> | <Level> | <message>
Get-Content 'C:\ProgramData\JenkinsAsService\agent.log' -Tail 50 -Wait

Log Rotation

Serilog handles log rotation automatically:

  • When agent.log exceeds 10MB, it rolls to agent_001.log, agent_002.log, etc.
  • Number of retained files is configurable via RetainedLogs (default: 3). Oldest files are permanently deleted (skips recycle bin).
  • Logs are appended across restarts — never wiped

Windows Event Log

Warnings and Errors are also written to the Windows Application event log under source JenkinsAsService. Check this when:

  • The file log is missing or corrupted
  • The service crashed before writing to the file
  • You need crash evidence across multiple restarts
Get-EventLog -LogName Application -Source JenkinsAsService -Newest 20

Common Issues

Message reference by severity

Log messages the service emits, by severity. Errors stop the service (or the current startup); Warnings are non-fatal — the watchdog keeps going. The topic sections below drill into the most common cases.

Log message / symptom Type Meaning & fix
'Connection:Url' is a mandatory field / 'Secret:Value' is a mandatory field Error A required field in appsettings.json is empty — fill it in.
Connection:Url must include an explicit port Error Write the port explicitly: https://jenkins:8443. A URL with no port is rejected; an explicit standard :443 is accepted.
Connection:Url is not a valid absolute URL Error Malformed URL — fix the value.
Cannot find java.exe Error Set Agent:JavaPath to the JDK bin folder, or set JAVA_HOME.
DPAPI decryption failed / TPM decryption failed / env var or credential not found Error The secret can't be decrypted or read on this machine — re-run update-secret (DPAPI/TPM keys are machine-bound and don't move between hosts).
Service failed — shutting down Error A non-transient failure (bad config, unresolvable secret, missing Java) — check the logged exception; the service stops so SCM recovery can restart it.
Watchdog: Failed to download or start the agent — will retry Error Jar download or process launch failed — check the jar URL, disk permissions, and Java. Retried automatically with backoff.
Watchdog: Max retries (N) exceeded — the agent keeps crashing. Stopping the service. Error A persistent crash-loop hit Recovery:MaxRetries; the service stops itself so Windows Service Recovery restarts it. Enable DebugMode and inspect the exit codes.
Connection:Url uses http — agent secret will be sent unencrypted. Consider HTTPS. Warning Plain HTTP sends the secret in cleartext. Use HTTPS. (Not blocked.)
Connectivity test to <host>:<port> timed out / failed Warning Controller unreachable — check firewall, DNS, the port, and that Jenkins is running.
Watchdog: Jenkins unreachable — will keep retrying. Warning Controller down during (re)connect. Retried indefinitely with backoff; does not count toward MaxRetries.
Watchdog: Agent emitted N SEVERE event(s) before exiting. Warning The agent logged SEVERE lines before dying — check the controller logs and that AgentName/Secret match the node exactly.
Watchdog: <transport> transport failed to stabilise — falling back to <other>. Warning Connection:Method = Auto toggled WebSocket ↔ direct-TCP inbound. If it flip-flops, make sure the intended transport is enabled on the controller.
Could not restrict ACL on agent secret file Warning The defense-in-depth ACL couldn't be applied; the secret file is still usable and already lives in a restricted folder — check the data-folder permissions.
Warning: could not delete secret file <path>. Delete it manually. Warning Emitted by update-secret --secret-file when the file it consumed could not be removed (held open, or ACL denies delete). The secret was applied, but a plaintext copy remains on disk — delete the named file manually.
Agent connects then disconnects randomly Warning Connection:AgentName and Secret:Value must match the Jenkins node config exactly; check network stability.

Service starts and immediately stops

Every cause is one of the Error rows above — a mandatory field is empty, the URL is malformed or has no explicit port, Java can't be found, or the secret can't be resolved on this machine. The service stops itself (rather than faulting) so Windows Service Recovery can act, so a restart loop with no agent is the signature.

Read agent.log from the data directory; if it is empty, the failure happened before the file sink existed — check the Event Log. The pre-flight validation error always names both the reason and the full path of the appsettings.json it read, which is the fastest way to spot a service pointed at a different install.

Jar download problems

  • HTTP error during download — verify Connection:Url and that the controller serves /jnlpJars/agent.jar. The download is retried by the supervision loop with backoff; it never counts toward MaxRetries.
  • Download hangs — network or proxy. The named HttpClient has a standard resilience handler (retry, circuit breaker, timeout), so a genuine hang shows up as repeated timeout warnings rather than a stuck service.
  • Repeated full downloads instead of 304s — the cached jar failed its SHA-256 check (tampered, or truncated by something outside the service) and was deliberately re-fetched, or the controller sends no ETag. Check what else writes to the agent\ cache directory; nothing else should.
  • TLS failure with a pin configured — Connection:ControllerCertThumbprint replaces chain trust for this download. After a controller certificate renewal the pin must be updated, or the download fails while everything else looks healthy.
  • Behind a proxy: the jar downloads but the node never comes online — the classic symptom of configuring one side only. Connection:Proxy covers the .NET jar download; the Java agent's own long-lived connection is the JVM's and ignores it. Pass the JVM flags too, via Agent:CustomArguments: -Dhttps.proxyHost=… -Dhttps.proxyPort=….
  • A ProxyBypass entry seems to be ignored — entries are turned into whole-URI anchored regexes for you, because WebProxy.BypassList matches the entire URI rather than the hostname. A pattern written by hand elsewhere as just a host would silently never match. Check the startup line that logs the chosen proxy: the selection is logged in the first few lines of agent.log, so a misrouted download is visible immediately.
  • The service refuses to start with a proxy message — deliberate. Connection:Proxy is parsed at startup so a malformed address fails loudly instead of looking like an unreachable controller for the next hour. Use host:port, a full URL, empty for the system proxy, or direct to bypass.

Agent connects but disconnects randomly

  • Check watchdog log entries: search for Watchdog: in agent.log
  • The watchdog will auto-recover with exponential backoff. Note a controller that is merely unreachable is retried indefinitely and does not count toward MaxRetries — only real agent crashes do.
  • If Watchdog: Max retries (N) exceeded — the agent keeps crashing. Stopping the service. appears, consecutive crashes hit the limit and the service stops itself so Windows Service Recovery can restart it (see Service Recovery). Set Recovery:MaxRetries to 0 for infinite retries. The issue is persistent — check:
    • Connection:AgentName matches the node name in Jenkins exactly (case-sensitive)
    • Secret:Value is correct (regenerate in Jenkins if unsure)
    • Jenkins controller logs for rejection reasons
    • Network stability between the agent and controller

Watchdog keeps restarting

If the agent repeatedly dies and recovers:

  • Enable Logging:DebugMode: true for detailed Java output
  • Look for patterns in agent.log — the watchdog logs exit codes before each restart
  • Common causes: Java OOM (increase heap via Agent:CustomArguments), Jenkins controller restarts, network drops

Debug Mode

Set Logging:DebugMode to true in appsettings.json to enable verbose Java agent output in the log file. This captures all Java stdout/stderr including remoting/JNLP handshake details.

No restart needed — that is the point

Save the file and the level changes within a second or two; the service logs “Logging:DebugMode changed to true — log level is now Debug. No restart required.” at Warning, so the change is visible in the log and the Event Log with a timestamp.

Restarting to enable debug logging would kill the agent and destroy the state you were trying to observe — and on a build node, drop a running build. Everything else in the config is still read at startup only. See Configuration → Live debug logging.

Uninstall took my logs

Expected, and unprompted: uninstall removes the install folder and %ProgramData%\JenkinsAsService — logs, the cached agent.jar, and the work\ tree. Copy anything you need out before uninstalling. An in-place upgrade keeps the data folder in full; only a genuine uninstall clears it.

This changed deliberately: leaving appsettings.json behind meant leaving a file holding the agent secret on a machine the product had supposedly been removed from. The secret is also cleared from its own store — TPM key, Credential Manager entry or machine environment variable. One exception is reported rather than silently skipped: a Credential Manager entry written with --impersonate lives in that user's vault, which the SYSTEM-run uninstall cannot reach, so remove it with cmdkey /delete:JenkinsAsService/AgentSecret while logged on as that account. Details in Installation → What uninstall removes.

After a manual (non-MSI) removal there is no custom action to run the cleanup, so do it yourself:

.\JenkinsAsService.exe purge

Service Recovery (Windows-Level)

The built-in watchdog handles Java process crashes. For full service host crashes (the .NET process itself dying), the MSI installer configures Windows service recovery automatically:

  • First / Second / Third failure: Restart the Service (after 10 seconds)
  • Reset fail count after: 1 day

Applied during installation by the ConfigureRecovery custom action — no manual configuration needed. Verify or re-apply it at any time:

sc.exe qfailure Jenkins
& "$env:ProgramFiles\Jenkins\JenkinsAsService.exe" configure-recovery

Re-applying is safe and idempotent, and a repair (msiexec /f) does it for you.

Service is running as LocalSystem

Check the identity with:

(Get-CimInstance Win32_Service -Filter "Name='Jenkins'").StartName

It should read NT SERVICE\Jenkins (or whichever account you chose). If it reads LocalSystem, the install came from a .exe bundle built before this was fixed: the bundle forwarded an empty SERVICE_ACCOUNT, and an empty property on the msiexec command line overrides the package default rather than deferring to it, so the service was registered with no account name at all.

This matters — LocalSystem is a full-privilege account, and the whole point of the default identity is that a pipeline running under the agent cannot write the install folder. Upgrading with a current .exe corrects it, keeping your configuration, secret and data folder. To confirm afterwards, re-run the command above.
