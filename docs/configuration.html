Configuration

Configuration File

The service reads its settings from appsettings.json, located in the same directory as the executable. The Jenkins section is grouped into topic sub-sections — Connection, Secret, Agent, Hardening, Logging, and Recovery. Settings below are written as Section:Key.

The MSI wizard collects most of these across three pages — JenkinsConfigDlg (URL, secret, node name, Java), SecurityOptionsDlg (secret protection mode) and Advanced Options (AdvancedOptionsDlg: transport, certificate pin, ViaFile, environment sanitization, logging and recovery). Fields left untouched keep their defaults, and anything you edit by hand afterwards survives upgrades — see Config migration on MSI upgrade.

Settings Reference

Setting Required Default Description
Connection:Url Yes — Full Jenkins URL including port. The port must be written explicitly — a URL with no port is rejected, but an explicitly-specified standard :443 (e.g. a reverse-proxied controller) is accepted. Example: https://jenkins.example.com:8443
Connection:Method No Auto Agent transport: Auto, WebSocket, or Https (direct TCP inbound). See Connection method.
Connection:AgentName No Machine hostname The agent/node name as configured in Jenkins. Case-sensitive.
Connection:ControllerCertThumbprint No (empty) SHA-256 thumbprint to pin the controller's TLS certificate for the agent.jar download. See Certificate Pinning.
Connection:Proxy No (empty) Proxy for the agent.jar download. Empty inherits the system/WinHTTP proxy; direct (or none) bypasses proxies entirely; anything else is an explicit address. See Proxy.
Connection:ProxyBypass No (empty) Hosts that bypass an explicit Connection:Proxy — semicolon/comma-separated, * wildcards allowed. Ignored unless an explicit proxy is set.
Secret:Value Yes — The JNLP secret (or, depending on Secret:Mode, the ciphertext / env-var name / credential target). Case-sensitive.
Secret:Mode No Unprotected How Secret:Value is stored/resolved. See Secret Protection Modes below.
Secret:DpapiScope No Machine DPAPI scope when Secret:Mode is Dpapi: Machine (any local process can decrypt) or User (only the encrypting identity). See DPAPI Scope.
Secret:ViaFile No true Pass the resolved secret to the Java agent as -secret @<file> (an ACL-restricted file) instead of inline on the command line, keeping it out of the process table. See Secret off the command line.
Agent:JavaPath No JAVA_HOME env var Full path to the JDK/OpenJDK bin folder. Example: C:\Program Files\Java\jdk-21.0.2\bin
Agent:CustomArguments No (empty) Additional arguments passed to java.exe. Space-separated, supports quoted values and escaped quotes (\"). Example: -noCertificateCheck
Agent:DataDirectory No %ProgramData%\JenkinsAsService Writable directory root for runtime artifacts, kept separate from the read-only install folder. Holds logs + secret file at the root, the cached agent.jar under agent\, and the Jenkins -workDir under work\. Env vars are expanded. The MSI sets this to the chosen DATAFOLDER. See Data directory split.
Hardening:SanitizeEnvironment No true Launch the Java agent with a deny-by-default environment (curated allow-list only), preventing the service's environment block from leaking into pipeline scripts. See Environment sanitization.
Hardening:AllowedEnvironmentVariables No (empty) Extra environment variable names (semicolon/comma-separated, case-insensitive) to pass through to the agent when Hardening:SanitizeEnvironment is on. Example: GRADLE_USER_HOME;MAVEN_OPTS.
Logging:DebugMode No false true to enable debug-level logging, false to disable. Applied live — editing this in appsettings.json takes effect within seconds, with no service restart. See Turning debug logging on without a restart.
Logging:CompactLog No false true to write CLEF (Compact Log Event Format) JSON to agent.clef instead of human-readable agent.log.
Logging:RetainedLogs No 3 Number of rolled log files to keep. Oldest are permanently deleted (skips recycle bin).
Recovery:MaxRetries No 0 Maximum consecutive agent crashes before the watchdog gives up and stops the service (so Windows Service Recovery / SCM can act, instead of leaving a dead agent behind a still-running service). A controller that is merely unreachable is retried indefinitely and does not count toward this limit. 0 = infinite (recommended).

Tip

Connection:AgentName defaults to the machine hostname if left empty. This is usually the correct value unless the Jenkins node name differs from the hostname.

Validation Flow

flowchart TD
    A["Read appsettings.json"] --> B["Bind to ServiceSettings via IOptions"]
    B --> C{Connection:Url filled?}
    C -->|No| D[Log error & stop]
    C -->|Yes| E{Secret:Value filled?}
    E -->|No| D
    E -->|Yes| F["Parse URL via System.Uri"]
    F --> G{Port written explicitly?}
    G -->|No port specified| D
    G -->|Yes| H[Resolve Java path]
    H -->|Not found| D
    H -->|Found| J["Enter supervision loop: connect → download agent.jar (ETag) → start, retrying with backoff"]
    J --> K[Supervise: restart on crash; give up only after MaxRetries consecutive crashes]

Java Path Resolution

The service resolves the Java executable in this order:

  1. Use Agent:JavaPath from config if set and java.exe exists at that path
  2. Fall back to JAVA_HOME environment variable root
  3. Fall back to JAVA_HOME\bin
  4. If none work → log error and stop

URL Validation

The Connection:Url is parsed using System.Uri:

  • Must be a valid absolute URI (parse failure → a clear configuration error)
  • The port must be written explicitly in the URL. A URL with no port is rejected; an explicitly-specified port is accepted even when it equals the scheme default (e.g. :443), so a reverse-proxied controller on the standard HTTPS port works. The check is scheme-agnostic — a non-HTTPS URL is not rejected here, only warned (see below).
  • TCP connectivity is tested asynchronously with a 2-second timeout

Connection Method

Connection:Method selects the transport the inbound agent uses to reach the controller:

ValueBehaviour
Auto (default) Start on WebSocket; if a run dies before reaching the 60s stability window, fall back to the other transport on the next restart (WebSocket ↔ Https). Whichever transport stabilises is kept. Self-correcting if one transport is blocked.
WebSocket Always connect via WebSocket (agent.jar -webSocket). Tunnels over the controller's HTTP(S) port — proxy/firewall friendly and the modern Jenkins-recommended transport. Requires WebSocket agents to be enabled on the controller.
Https Always use the direct TCP inbound port (no -webSocket) — the classic JNLP inbound behaviour. Requires the controller's "TCP port for inbound agents" to be enabled and reachable. (Named Https for brevity; the actual transport is a direct TCP connection, not literal HTTPS.)
Auto fallback heuristic

Fallback toggles only on a fast failure (a run that never reaches the stability window). A transport that connected and ran for a while before dying is not treated as a transport problem — the watchdog just restarts it on the same transport.

Secret Protection Modes

Secret:Mode controls how the Secret:Value is stored and resolved at runtime.

Mode Secret:Value field contains How resolved
Unprotected Plaintext secret Returned as-is
Dpapi Base64-encoded DPAPI ciphertext ProtectedData.Unprotect (non-portable; Machine or User scope — see below)
Tpm Base64-encoded RSA ciphertext (TPM-resident key) RSACng decrypt via the Platform Crypto Provider — see below
EnvironmentVariable Name of a system env var (default: JENKINS_SECRET) Environment.GetEnvironmentVariable(..., Machine)
CredentialManager Windows Credential Manager target name CredentialManager.GetCredentials(targetName).Password
Warning

DPAPI mode binds the secret to the machine. Moving appsettings.json to another machine will fail decryption. Re-run update-secret after a machine migration.

DPAPI Scope (Machine vs. User)

When Secret:Mode is Dpapi, Secret:DpapiScope chooses which key protects the secret:

Scope Who can decrypt Requirement
Machine (default) Any process on the machine None — works regardless of which identity wrote the secret
User Only the identity that encrypted it The secret must be written by the service account (see below)
User-scope identity constraint

User-scope DPAPI binds the ciphertext to a single Windows identity. Because the MSI writes the config as SYSTEM, a default install always uses Machine scope. To use User scope, the secret must be encrypted by the account that runs the service:

  • Works with a password-based dedicated account — run update-secret --mode Dpapi --dpapi-scope User --impersonate --username "DOMAIN\svc" (password via the JAS_IMPERSONATE_PASSWORD env var).
  • Not compatible with virtual accounts (NT SERVICE\Jenkins) or gMSA — they cannot be interactively logged on, so they cannot run the encryption step. Use Machine scope, EnvironmentVariable, or CredentialManager for those identities.

TPM 2.0 mode

Secret:Mode: Tpm encrypts the secret with a non-exportable RSA-2048 key held inside the machine's TPM, via the Microsoft Platform Crypto Provider. Unlike DPAPI machine-scope — whose key is software-derivable by any local admin/SYSTEM — the TPM private key never leaves the chip, so the ciphertext is bound to this physical machine and cannot be exfiltrated even by a full administrator.

  • Protect: the elevated installer (or update-secret) creates a persistent machine-scoped key (JenkinsAsService-AgentSecret) and RSA-OAEP-SHA256 encrypts the secret into Secret:Value.
  • Resolve: the service opens the same TPM key and decrypts. Because the key is created by SYSTEM but used by the low-privilege service account, the installer grants that account use-rights on the key — pass --service-account to update-secret (the MSI does this automatically).
Requirements & binding

Requires a TPM 2.0 with the Platform Crypto Provider present. The key is bound to the machine, not to platform/PCR state, so routine firmware and Windows updates do not break decryption. Clearing/resetting the TPM or moving to another machine invalidates the ciphertext — re-run update-secret --mode Tpm there.

Post-quantum cryptography (deliberately deferred)

For maintainers: a post-quantum secret-protection mode (ML-KEM/ML-DSA) has been evaluated and intentionally not implemented. Do not add one until the technology matures — the current trade-offs make it cost without benefit here. The reasoning:

  • Wrong primitive / no in-process signatures. ML-DSA is a signature algorithm; this service signs nothing in-process. The encryption-side primitive is ML-KEM, but a KEM needs a private key.
  • Key custody defeats the point on a single node. The ML-KEM private key would have to live on the same machine, wrapped by TPM/DPAPI — so the root of trust stays TPM/DPAPI and PQC adds nothing against a local attacker. The secret is local, machine-bound and rotatable, so it is not a “harvest-now-decrypt-later” target.
  • No TPM-resident ML-KEM yet. Current TPM 2.0 chips can’t store an ML-KEM key, so the PQC private key falls back to software wrapping — reintroducing the classic weak link.
  • APIs are experimental. .NET’s System.Security.Cryptography.MLKem / MLDsa are marked [Experimental] (SYSLIB5006) and require very recent OS crypto providers (Windows 11 24H2 / Server 2025 CNG, or OpenSSL 3.5+). Baking an experimental, narrow-availability API into a portable, locked-restore, SBOM-pinned service is a regression in posture.
When to revisit

Reconsider once the PQC APIs leave [Experimental] and OS/TPM support is broad — or if the architecture ever gains off-box key custody (an ML-KEM private key held in a remote HSM/KMS), which is the only design that genuinely defeats harvest-now-decrypt-later. The real quantum surfaces for this system are the controller TLS channel (ML-KEM-hybrid TLS — the Jenkins controller / JVM / OS’s responsibility) and code signing (Authenticode, pending ML-DSA support in the CA ecosystem). Until then: rotate the JNLP secret at the PQC transition.

Certificate Pinning

Set Connection:ControllerCertThumbprint to the SHA-256 thumbprint of the Jenkins controller's TLS certificate to defend against a MITM that presents a different but chain-trusted certificate (e.g. a rogue internal CA). When set, the agent.jar download accepts the connection only if the server certificate's thumbprint matches — the pin replaces chain trust. Separators (colons, spaces) and case are ignored.

Scope of the pin

This pins the .NET agent.jar download only. The Java agent's own control-channel TLS is handled by the JVM, not .NET. To pin that connection as well, pass the controller certificate to the agent via Agent:CustomArguments (the Jenkins remoting agent accepts -cert <PEM>).

Proxy

Connection:Proxy controls how the service reaches the controller to fetch agent.jar:

ValueBehaviour
(empty — default) Inherit the machine/WinHTTP proxy configuration, exactly as before this setting existed. Note a service runs as a different identity than you do, so a proxy configured under your user account is not necessarily visible to it — set it explicitly if the download fails but a browser on the same box works.
direct or none Bypass proxies entirely and connect straight out. Use when a machine-wide proxy exists but the Jenkins controller is internal.
proxy.example.com:8080
http://proxy.example.com:8080		 Use this proxy. A bare host:port is accepted and assumed http. A malformed value fails at startup with a clear message rather than looking like an unreachable controller later.

Connection:ProxyBypass lists hosts that skip an explicit proxy — semicolon- or comma-separated, with * wildcards, e.g. *.corp.local;jenkins.internal. Local addresses always bypass. The chosen proxy is logged at startup, so a misrouted download is visible in the first few lines of agent.log.

This covers the jar download only — not the agent's own connection

These settings apply to the .NET-side agent.jar download. The Java agent's long-lived connection to the controller is the JVM's, and ignores them entirely. To route that through a proxy as well, pass the JVM's own flags via Agent:CustomArguments, for example -Dhttps.proxyHost=proxy.example.com -Dhttps.proxyPort=8080 -Dhttp.nonProxyHosts="*.corp.local". A node whose jar downloads succeed but which never comes online is the classic symptom of configuring one and not the other.

Turning debug logging on without a restart

Logging:DebugMode is re-read while the service runs. Edit appsettings.json, save, and within a second or two the log level changes — the service logs "Logging:DebugMode changed to true — log level is now Debug. No restart required." and starts emitting the verbose Java agent output.

This matters because the alternative is restarting the service to diagnose it, which kills the agent, drops the Jenkins node, and destroys the very state you were trying to observe. Turn it back off the same way when you are done — debug output is verbose and will roll your log files faster.

Only the log level is live

Every other setting is still read once at startup. Changing the URL, the secret, the transport or the data directory needs a restart.

Secret off the command line

By default (Secret:ViaFile: true) the resolved JNLP secret is never placed on the Java agent's command line. It is written to an ACL-restricted file (inheritance broken; SYSTEM, Administrators, and the service account only) and handed to the agent as -secret @<file>. This keeps the secret out of the process table — otherwise any local administrator could read it for the agent's entire lifetime via Get-Process or WMI Win32_Process.CommandLine. The file is overwritten on each restart and deleted on service stop. Set Secret:ViaFile: false only if your Jenkins remoting version predates @file support.

Environment sanitization

With Hardening:SanitizeEnvironment: true (default) the Java agent is launched with a deny-by-default environment: only a curated allow-list of variables the JVM and common Windows build tooling need (SystemRoot, PATH, TEMP, JAVA_HOME, ProgramFiles, …) is passed through. This stops the service's own environment block — which may carry host secrets or tokens — from being inherited by untrusted pipeline scripts that run inside the agent. If a build needs an extra host variable, add it to Hardening:AllowedEnvironmentVariables (semicolon/comma-separated, case-insensitive) rather than disabling the feature.

Data directory split (binaries vs. runtime data)

The service keeps its read-only binary and its writable runtime data in two separate locations:

LocationDefaultContentsACL
Install folder C:\Program Files\Jenkins JenkinsAsService.exe, appsettings.json Read/Execute (default Program Files) — the agent account cannot write
Data folder (Agent:DataDirectory) C:\ProgramData\JenkinsAsService agent.log/.clef + .agent-secret at the root; cached agent.jar (+ .etag/.sha256) under agent\; Jenkins -workDir under work\ Service account granted write (set by the MSI)

Because the install folder is not writable by the agent identity, a malicious pipeline running inside the agent cannot overwrite the service binary and wait for a restart — a local privilege-escalation / persistence vector that a single shared folder can't close (the same identity needs write for data but must not have it for the binary). The MSI sets Agent:DataDirectory to the chosen DATAFOLDER; for portable/manual deployments the service defaults to %ProgramData%\JenkinsAsService and creates it on first run.

Inside the data folder the cached agent.jar and its integrity sidecars live in the agent\ subfolder, kept out of the work\ subfolder (the Jenkins -workDir) where builds churn — so a git clean or a workspace-path collision can't clobber the binary the watchdog launches. On download the jar's SHA-256 is recorded next to it; on every subsequent start, if the controller answers the ETag check with 304 Not Modified, the cached jar is re-hashed and compared — any mismatch (tamper or corruption) forces an unconditional re-download rather than launching the altered jar. This is trust-on-first-use local-integrity checking; to also pin who the jar came from, set Connection:ControllerCertThumbprint.

CLI: update-secret

The JenkinsAsService.exe update-secret subcommand writes (or re-writes) appsettings.json with the secret processed for the chosen mode. Used by the MSI installer and manually.

JenkinsAsService.exe update-secret [options]

  Secret input (pick one)
  --secret <value>       Plaintext secret (command-line)
  --secret-file <path>   Read from file (deleted after reading)
  --secret-env <var>     Read from named environment variable

  Core settings
  --url <value>          Jenkins controller URL (explicit port required)
  --mode <value>         Dpapi | Tpm | EnvironmentVariable | CredentialManager | Unprotected
  --dpapi-scope <value>  Machine (default) | User  (User requires writing as the service account)
  --method <value>       Connection:Method — Auto | WebSocket | Https
  --thumbprint <value>   SHA-256 thumbprint of the controller cert to pin (agent.jar download)
  --agent-name <value>   Node name (default: hostname)
  --java-path <value>    Java bin folder (default: JAVA_HOME)
  --service-account <a>  Service account granted read on the config; hardens the appsettings.json ACL

  Optional settings (also collected by the installer's Advanced Options page)
  --via-file <bool>      Secret:ViaFile — pass the secret as -secret @<file> (default: true)
  --custom-args <value>  Agent:CustomArguments
  --sanitize-env <bool>  Hardening:SanitizeEnvironment (default: true)
  --allowed-env <names>  Hardening:AllowedEnvironmentVariables (; or , separated)
  --debug <bool>         Logging:DebugMode
  --compact-log <bool>   Logging:CompactLog — CLEF JSON output
  --retained-logs <n>    Logging:RetainedLogs (default: 3)
  --max-retries <n>      Recovery:MaxRetries (0 = infinite)

  Modes
  --silent               Non-interactive (all values from flags)
  --impersonate          Run the write as a different user (Credential Manager / User-scope DPAPI)
  --username <value>     Username for impersonation (DOMAIN\user)
  --merge                Apply only the optional settings supplied, leaving everything else untouched
  --set-data-dir <path>  Write only Agent:DataDirectory
  --upgrade              Reconcile appsettings.json to the current schema; preserve the existing secret
  --help                 Show usage

--merge, --set-data-dir and --upgrade exist because an MSI custom-action command line is capped at 255 characters — the installer splits the work across several calls. They are equally usable in a hand-rolled deployment script.

Tip

In silent mode with --impersonate, provide the password via the JAS_IMPERSONATE_PASSWORD environment variable to avoid command-line exposure.

Config migration on MSI upgrade

On an in-place MSI upgrade, the installer runs update-secret --upgrade as SYSTEM. It first reconciles appsettings.json to the current schema: settings the new version adds are written at their POCO defaults, settings the schema no longer defines are removed, and every value still in the schema — including the secret — is preserved as-is.

The check for an existing secret is a raw-string presence check on Jenkins:Secret:Value, not a decryption attempt — so it works as SYSTEM regardless of which identity the secret is bound to. A secret protected with User-scope DPAPI, TPM, or Credential Manager under the service account is preserved untouched rather than re-written. If no secret is present after reconciliation, the upgrade performs a full write from the --secret/--url/--mode values supplied to the CA; with none supplied, it fails the same way a fresh silent install with no secret does.

Warning

Reconciliation prunes unrecognized keys. Hand-added settings under Jenkins or Telemetry, and any other top-level section, are removed on the next upgrade — configure only documented settings.

Telemetry (OpenTelemetry)

Disabled by default. Set Enabled: true to export metrics via OTLP.

Setting Default Description
Enabled false Enable OpenTelemetry metrics export
OtlpEndpoint http://localhost:4317 OTLP gRPC endpoint (Datadog agent, Grafana Alloy, etc.)
ServiceName JenkinsAsService service.name resource attribute

Exported metrics:

  • jenkins_agent_restarts_total — counter, increments on each successful agent restart
  • jenkins_agent_severe_events_total — counter, increments on each SEVERE: log line
  • .NET runtime metrics (GC, thread pool, memory) via OpenTelemetry.Instrumentation.Runtime
