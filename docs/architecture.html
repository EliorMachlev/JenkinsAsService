Runtime File Layout (Installed)

Binaries and runtime data live in separate locations: the install folder stays read-only to the agent identity (so a build step can't overwrite the service .exe), while everything the service writes goes under %ProgramData%\JenkinsAsService. The cached agent.jar sits in its own agent\ subfolder, isolated from the Jenkins -workDir under work\, so workspace churn can't clobber the binary the watchdog launches.

C:\Program Files\Jenkins\          # Read-only install folder (binaries)
├── JenkinsAsService.exe     # Self-contained .NET 10 executable
└── appsettings.json         # Configuration

C:\ProgramData\JenkinsAsService\   # Writable data folder (Agent:DataDirectory)
├── agent.log                # Serilog rolling log (or agent.clef in CompactLog mode)
├── agent_001.log            # Rolled log (size-based; RetainedLogs kept)
├── .agent-secret            # ACL-restricted secret file (-secret @file), deleted on stop
├── agent\                   # Isolated agent-binary cache
│   ├── agent.jar            # Downloaded from Jenkins (ETag cached)
│   ├── agent.jar.etag       # Stored ETag for conditional GET
│   └── agent.jar.sha256     # Recorded hash; re-verified before each launch
└── work\                    # Jenkins -workDir (remoting/, workspace/, build output)

Service Lifecycle

ExecuteAsync (Start)

JenkinsAgentWorker.ExecuteAsync() is the BackgroundService entry point:

  1. Log session banner — === SERVICE STARTING (PID: ...) ===
  2. ValidateSettings() — Checks mandatory fields; requires the URL to carry an explicit port
  3. ResolveJavaPath() — Checks JavaPath config → JAVA_HOME → JAVA_HOME\bin
  4. RunSupervisionLoop() — Brings the agent up (connectivity → jar download → start) and supervises it. Because bring-up lives inside the loop, a transient outage at boot (DNS/network not up, controller mid-restart) retries with backoff instead of faulting the service.

A non-transient failure (bad config, unresolvable secret, missing Java) is caught and the host is shut down cleanly via IHostApplicationLifetime.StopApplication() — SCM recovery, if configured, then restarts the service.

StopAsync

  1. Logs the stop request
  2. Sets a _stopping flag before killing, so the supervision loop treats the kill-induced exit as an intentional stop, not a crash to be counted/recovered
  3. Kills the agent process tree and deletes the on-disk secret file
  4. Logs confirmation

Execution Model

The Java process is created behind an IAgentProcessLauncher seam (production impl wraps System.Diagnostics.Process; a fake drives the supervision loop in tests without spawning java.exe):

  • ProcessStartInfo.ArgumentList for safe argument passing (no shell interpretation)
  • RedirectStandardOutput + RedirectStandardError with async event handlers
  • OutputDataReceived / ErrorDataReceived → ParseAgentOutput():
    • INFO: ... → LogInformation
    • WARNING: ... → LogWarning
    • SEVERE: ... → LogError
    • Everything else → LogInformation (or LogDebug in debug mode)

Watchdog & Auto-Recovery

RunSupervisionLoop() is event-driven (no polling) and has two states. When no agent is running it is in bring-up: connectivity → jar download → start, with exponential backoff between attempts. When an agent is running it awaits Task.WhenAny(agent.Exited, Task.Delay(StabilityMs)), where the exit signal is a TaskCompletionSource completed by the launcher's process-exit event.

The key distinction is crash vs. unreachable: only real agent crashes count toward MaxRetries. A controller that is simply unreachable is retried in bring-up indefinitely and never trips give-up, so a maintenance window can't permanently stop the service. When consecutive crashes do exceed MaxRetries, the loop calls IHostApplicationLifetime.StopApplication() so the service actually stops (and Windows Service Recovery / SCM can act) instead of leaving a dead agent behind a still-RUNNING service.

flowchart TD
    S[Supervision Loop] --> SG{Stopping or cancelled?}
    SG -->|Yes| SX["Kill any live agent (reaps a late-started one), return"]
    SG -->|No| Q{Agent running?}
    Q -->|No — bring-up| BU["Backoff, then: TCP connectivity → ETag conditional GET agent.jar → start"]
    BU -->|Unreachable or start failed| R1[Retry indefinitely — does NOT count toward MaxRetries]
    R1 --> S
    BU -->|Started| S
    Q -->|Yes| W[Await exit signal OR 60s stability timer]
    W -->|Shutting down _stopping| X[Return — StopAsync handles cleanup]
    W -->|60s elapsed, still alive| D[Reset crash counter on stability]
    D --> S
    W -->|Process exited| E[Log SEVERE count, capture exit code, kill, Auto-transport fallback]
    E --> F{Consecutive crashes exceed MaxRetries?}
    F -->|Yes| G["StopApplication() — service stops so SCM can recover"]
    F -->|No| S
  • Bring-up vs. live: connectivity, download and start all happen in the loop's bring-up state, so both first launch and recovery share one code path (and one backoff).
  • Crash counter: incremented only on a real agent exit; reset to 0 after 60s of stability. MaxRetries = 0 means infinite (default).
  • Unreachable controller: retried forever in bring-up without incrementing the crash counter — outages never cause a permanent give-up.
  • Exit signal: the launcher captures its exit TaskCompletionSource in a local (not a shared field), so a late exit from a killed process can't complete a newer process's signal and trigger a spurious restart.
  • Shutdown gate: every pass through the loop top checks _stopping/cancellation and kills (idempotently) before returning. This reaps an agent that bring-up started after StopAsync's own kill ran (which was a no-op while nothing was running yet), so a stop during bring-up can't orphan a freshly launched java.exe. The loop also snapshots the agent handle per iteration — StopAsync runs on another thread and nulls the shared field.
  • Backoff: 10s → 20s → 40s → 80s → ... capped at 300s.
  • Auto-transport fallback: on a fast crash in Auto mode, the next bring-up toggles WebSocket ↔ direct-TCP.
  • SEVERE counter: _severeCount is Interlocked.Increment-ed per SEVERE line; read and reset via Interlocked.Exchange on each exit.

HTTP Resilience

The HttpClient used by HttpJarDownloader is registered as a named client ("JarDownloader") with AddStandardResilienceHandler() from Microsoft.Extensions.Http.Resilience. This provides automatic retry, circuit breaker, and timeout. Separate from the watchdog's recovery loop.
